⚠️ Cipher Naming Issue — Key Finding

OpenSSL Format vs IANA Format

The two backends report identical ciphers under different naming conventions. openssl reports in OpenSSL shorthand (e.g. ECDHE-RSA-AES256-GCM-SHA384), while nmap reports in IANA full names (e.g. TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384). Both formats exist in approved_ciphers.csv so compliance lookups succeed for both backends — but results are not directly string-comparable across backends.

Exception: TLS 1.3 ciphers

TLS 1.3 names (e.g. TLS_AES_256_GCM_SHA384) are identical in both backends and share a single CSV entry. No mapping needed for TLS 1.3.

Conclusions & Recommendations

  • Fair comparison: openssl with --ciphers 0 (unlimited) is 5–24× slower than nmap for equivalent full-enumeration scans.
  • Cipher coverage: nmap and openssl unlimited find near-identical cipher counts on most targets. nmap finds slightly more TLS 1.3 ciphers (3 vs 1) on google/github due to how it probes TLS 1.3 suites.
  • Cipher naming: OpenSSL shorthand and IANA names are both present in approved_ciphers.csv so compliance ratings are accurate on both backends. Cross-backend diffs require name normalisation before string comparison.
  • Recommended next step: Add an OpenSSL ↔ IANA name normalisation layer so report diffs are backend-agnostic.
  • Compliance verdict: google.com still accepts TLS 1.0/1.1 (NOT_APPROVED). github.com is TLS 1.2+ only (compliant). badssl.com test targets behave exactly as advertised.
